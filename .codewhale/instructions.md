# docsforge 项目协作约定

本文件是本仓库 Codewhale 项目的**项目级指令**，每个会话都应遵守。

## 需求讨论与落盘

用户的核心诉求：**需求讨论的结论不允许只停留在对话里**——聊着聊着会忘。
必须落到持久化文档，让未来的会话能"读文件而不是重聊"。

### 单一事实来源

- `docs/design/roadmap.md` 是需求的**唯一事实来源**：
  - 含"功能全景 + 实施顺序 + 研发编号（S1–S4 / L1–L8）+ 验收红线"。
  - 末尾"第七章 需求讨论台账"是**决策落盘区**，每次讨论结论都追加到那张表。

### 每次需求讨论的行为准则

1. **开始聊需求前**：先读 `docs/design/roadmap.md`，对照现有功能判断归属
   （认识/产出/质量/集成）与内部编号；已记录的需求不重复讨论。
2. **讨论中**：主动把字段/界面/验收细节的定稿说清，避免留模糊。
3. **讨论出结论时**：**主动提醒并写回 roadmap**——
   - 新需求 / 细节定稿 → 追加到"需求讨论台账"表；若该功能有对应编号章节，同步维护。
   - 状态：✅ 已实施 ｜ 🚧 实施中 ｜ 📋 待实施 ｜ ⚖️ 讨论中 ｜ ❌ 已否决（保留原因）。
4. **每一轮需求讨论的末尾**：若产生了待落盘的结论，主动询问是否写入台账，
   而不是等用户想起。用户同意后立即落盘。

### 需求状态迁移

- 完成某项功能时，除代码验证外，把 roadmap 对应格子改为 ✅，并在台账记录"已完成"。
- **S4 / L1 有"吃狗粮"验收红线**：docsforge 自己的 `docs/` 必须能被工具自驱动
  （S4 已实现；L1 待做）。完成这些功能时必须核对。
- 需求被否决时，在台账保留一行（标注原因），避免日后重复评估。

### 项目模块结构速览（讨论时的共同语言）

- `docsforge/scan.py` —— S4 多文件/目录/glob 扫描（`resolve_inputs` + `scan_files`，已实现）
- `docsforge/render.py` —— 渲染器按 **token 分派**（S1 已完成：`@register_renderer` 注册表 + `--token` 多值）
- `docsforge/drift.py` —— 生成区替换 + 漂移检查
- `docsforge/handlers/python_fastapi.py` —— 唯一内置语言适配器（S3 已完成：类/模块/配置项识别；L2 多语言待扩展）
- `docsforge.yaml` —— 目标形态 manifest（L1 落地前代码不解析）

架构主线：`tags`（解析注解）→ `registry/handlers`（按语言提取）→ `render`（渲染）
→ `drift`（生成区/漂移）→ `cli`（入口）。只有 handlers/ 语言相关，其余全语言无关。
